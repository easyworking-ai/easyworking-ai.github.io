## "챗봇이랑 뭐가 다른데?"

에이전트 도입을 논의할 때 가장 먼저 듣는 질문이다. 맞는 질문이다. 차이를 모르면 도입의 이유도 없다.

챗봇은 질문을 받고 답을 준다. "회의록 정리해줘" → 정리해준다. 끝이다. 답의 품질이 좋으면 쓸 만하다. 하지만 한 가지 일밖에 못 한다. 회의록을 정리하면서, 동시에 관련 이메일을 찾고, 일정을 확인하고, 결과를 캘린더에 등록하는 건 불가능하다. 챗봇은 한 번에 하나만 처리한다.

에이전트는 다르다. "회의록 정리하고, 거기서 나온 액션 아이템을 캘린더에 등록하고, 담당자에게 메일 보내줘"라고 하면, 에이전트는 이것을 여러 단계로 쪼개서 실행한다. 회의록 정리 → 액션 아이템 추출 → 캘린더 확인 → 메일 작성 → 발송. 각 단계에서 필요한 도구를 스스로 고르고, 중간에 문제가 생기면 다른 방법을 시도한다.

여기서 "스스로"가 핵심이다. 챗봇은 사용자가 단계를 지시한다. 에이전트는 사용자가 목표를 주면, 에이전트가 단계를 정한다.

## 실제 업무에서 이 차이가 만드는 것

### 케이스 1: 주간 보고서 작성

**챗봇 방식**

1. 사용자: "이번 주 매출 데이터 요약해줘" → AI가 요약
2. 사용자: "지난주랑 비교해줘" → AI가 비교
3. 사용자: "보고서 형식으로 정리해줘" → AI가 정리
4. 사용자: 이메일에 복사해서 발송

세 번을 물어봐야 하고, 마지막은 사람이 한다.

**에이전트 방식**

사용자: "이번 주 매출 보고서를 만들어서 팀에 메일로 보내줘. 지난주 대비 변화를 포함하고, 마감은 금요일 오전이라고 써."

에이전트:
1. 매출 데이터 확인 (도구: 데이터베이스 조회)
2. 지난주 데이터와 비교 (도구: 데이터베이스 조회)
3. 보고서 초안 작성
4. 이메일 작성 (도구: 이메일 API)
5. 사용자에게 초안 승인 요청
6. 승인 → 발송

사용자는 목표만 주고, 마지막 승인만 한다. 중간 단계는 에이전트가 알아서 한다.

### 케이스 2: 고객 문의 분류

채널에 들어오는 고객 문의를 "기술 지원", "결제", "일반"으로 분류하는 작업이 있다. 하루에 50개.

**챗봇 방식**: 문의를 하나씩 복사해서 AI에게 "분류해줘" → 분류 결과를 스프레드시트에 수동 입력. 50번 반복.

**에이전트 방식**: "메일함에서 오늘 문의를 가져와서 분류하고, 스프레드시트에 정리해. 기술 지원은 기술팀 채널로, 결제는 재무팀으로 전달해."

에이전트는 메일함을 읽고, 각 문의를 분류하고, 스프레드시트를 업데이트하고, 팀 채널에 메시지를 보낸다. 50개를 한 번에.

## 에이전트를 "언제" 쓸 것인가

에이전트가 항상 더 좋은 건 아니다. 다음 조건이 맞을 때 에이전트가 의미가 있다.

| 조건 | 이유 |
|---|---|
| 여러 단계가 필요하다 | 챗봇은 단계마다 사용자가 끼어들어야 한다 |
| 여러 도구를 써야 한다 | 챗봇은 도구를 직접 호출하지 못한다 |
| 같은 작업이 반복된다 | 에이전트 설정 비용이 반복 횟수로 회수된다 |
| 중간에 실패할 수 있다 | 에이전트는 실패 시 다른 경로를 시도한다 |

반대로, 한 번의 질문으로 끝나는 작업은 챗봇이 낫다. "이 영어 메일 번역해줘"를 에이전트로 할 필요는 없다. 에이전트는 설정하고 유지하는 데 비용이 든다. 단순한 작업을 에이전트로 포장하면, 설정 비용이 효율을 깎아먹는다.

## 도입 전에 확인할 것

에이전트가 멋대로 실행하면 안 되는 업무가 있다. 메일 발송, 결제 승인, 고객 데이터 수정. 이런 작업은 에이전트가 "한다"가 아니라 "초안을 만들고 사람이 승인하면 실행한다"로 설계해야 한다.

에이전트 도입에서 가장 위험한 것은 "다 알아서 하겠지"라고 맡기는 것이다. 현재 기술 수준에서 에이전트는 **확률적으로** 맞는 행동을 한다. 90%는 잘 하는데, 10%는 엉뚱한 짓을 한다. 메일 발송 같은 건 그 10%가 치명적이다.

실무에서는 에이전트가 할 수 있는 일과 할 수 없는 일을 명확히 나누고, 외부에 영향을 미치는 행위(메일 발송, 파일 수정, 결제)는 반드시 사람이 승인하는 단계를 넣는다. 이게 "에이전트를 안전하게 쓴다"는 뜻이다.
