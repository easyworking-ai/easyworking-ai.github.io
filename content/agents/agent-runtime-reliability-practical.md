## "더 똑똑한 모델로 바꾸면 되겠죠?"

에이전트가 실무에서 문제를 일으키면, 가장 먼저 하는 일은 모델을 바꾸는 것이다. GPT-4o에서 Claude로, Claude에서 Gemini로. 프롬프트를 다듬고, 온도를 0으로 내리고, few-shot 예시를 추가한다. 이런 시도의 8할은 실패한다. 왜냐하면 문제의 원인이 모델의 지능이 아니라 **실행 구조**에 있기 때문이다.

벤치마크 점수가 높은 모델을 써도, 에이전트는 여전히 중간에 멈추고, 도구 호출이 실패하고, 비용이 통제 불가능해진다. 더 똑똑한 모델은 "주어진 환경에서 더 나은 답을 낸다"는 뜻이지, "환경 자체의 문제를 해결한다"는 뜻이 아니다.

런타임 신뢰성 — 에이전트가 한 번 잘 되는 게 아니라 계속 잘 되게 만드는 것 — 을 판단하는 기준 5가지를 정리한다.

## 1. 지연 예산 (Latency Budget)

에이전트가 하나의 작업을 완료하는 데 얼마나 걸리는가. 단순한 질문이지만, 대부분의 팀이 이걸 측정하지 않는다.

에이전트가 5단계를 거쳐야 할 때, 각 단계는 모델 추론(3~15초) + 도구 호출(1~30초)로 이루어진다. 5단계면 최소 20초, 최대 200초. 사용자가 기다릴 수 있는 시간을 넘으면, 중간에 포기하거나 수동으로 처리한다.

실무에서 확인해야 할 것은 평균이 아니라 **최악의 경우**다. P99 지연(100번 중 1번 꼴로 발생하는 가장 느린 응답)이 5분이면, 그 1번 때문에 전체 워크플로가 멈춘다. 지연 예산을 설정하고, 그것을 넘으면 에이전트가 중간 결과를 사용자에게 보여주도록 설계해야 한다.

## 2. 도구 호출 비용 (Tool Call Cost)

에이전트가 도구를 호출할 때마다 비용이 발생한다. API 호출 비용, 데이터베이스 쿼리 비용, 컴퓨팅 비용. 에이전트가 한 작업에 도구를 10번 호출하면, 그 비용이 10배가 된다.

문제는 에이전트가 "같은 도구를 반복 호출"하는 경우다. 검색 도구로 결과를 받았는데, 그 결과를 이해하지 못하고 다시 검색. 또 다시 검색. API 호출 한도를 넘거나, 비용이 예상을 훌쩍 넘어간다.

실무에서는 도구 호출 횟수에 상한을 걸어야 한다. "하나의 작업에서 같은 도구를 최대 3번까지만 호출" 같은 규칙이다. 상한을 넘으면 에이전트가 중단하고, 사람에게 알린다. 비용 통제가 안 되는 에이전트는 쓸 수 없다.

## 3. 권한 경계 (Permission Boundary)

에이전트가 무엇을 할 수 있고, 무엇을 할 수 없는가. 이 경계가 명확하지 않으면, 에이전트는 "도움이 되려고" 위험한 행동을 한다.

읽기 권한만 줘야 할 곳에 쓰기 권한을 주면, 에이전트가 데이터를 수정한다. 내부 데이터만 봐야 할 곳에 외부 API 접근을 주면, 에이전트가 외부 서비스에 데이터를 보낸다. "도움이 되려고" 한 행동이 보안 사고가 된다.

실무에서 권한은 **최소 권한 원칙**으로 설정한다. 에이전트가 현재 작업에 필요한 권한만 주고, 작업이 끝나면 회수한다. 특히 파일 삭제, 메일 발송, 결제 같은 행위는 에이전트가 직접 하지 못하게 막고, 사람의 승인 단계를 넣는다.

## 4. 상태 복구 (State Recovery)

에이전트가 5단계 작업 중 3단계에서 실패하면, 어떻게 되는가.

좋은 설계: 1~2단계 결과를 보존하고, 3단계부터 재시작.
나쁜 설계: 처음부터 다시 시작. 1~2단계를 다시 실행하면서 비용이 두 배로.

에이언트가 중간에 실패했을 때, 어디까지 했는지를 기억하고 거기서부터 재개할 수 있어야 한다. 이걸 "상태 복구"라고 한다. 상태 복구가 없는 에이전트는, 실패할 때마다 처음부터 시작하고, 이건 실무에서 쓸 수 없다.

## 5. 실행 환경 (Execution Environment)

에이전트가 코드를 실행해야 할 때, 그 코드가 어디서 실행되는가. 샌드박스(격리된 환경)에서 실행되면 안전하다. 사용자의 실제 머신에서 실행되면, 에이전트가 시스템 파일을 건드릴 수 있다.

실무에서는 에이전트가 실행하는 코드를 샌드박스로 격리하고, 파일 시스템 접근을 제한하고, 네트워크 접근을 화이트리스트로 관리한다. "에이전트가 뭘 실행할지 모르니까, 일단 다 허용"은 사고의 원인이다.

## 실무 적용: 무엇을 먼저 확인할 것인가

에이전트를 도입하거나 평가할 때, 이 5가지를 순서대로 확인한다.

1. **지연 예산**: 하나의 작업이 끝나는 데 얼마나 걸리는가? (측정)
2. **비용**: 하나의 작업에 도구를 몇 번 호출하는가? (측정)
3. **권한**: 에이전트가 할 수 있는 일의 범위는? (문서화)
4. **복구**: 실패했을 때 어디서부터 재시작하는가? (테스트)
5. **환경**: 코드가 어디서 실행되는가? (확인)

이 중 하나라도 "모르겠다"면, 그것부터 해결해야 한다. 더 똑똑한 모델을 넣는 건 그 다음이다.
