## 「チャットボットと何が違うの？」

エージェント導入を議論する時、最も先に聞かれる質問だ。正しい質問だ。違いを知らなければ導入の理由もない。

チャットボットは質問を受け取って答える。「議事録整理して」→整理してくれる。終わりだ。答えの品質が良ければ使える。しかし一つのことしかできない。議事録を整理しながら、同時に関連メールを探し、スケジュールを確認し、結果をカレンダーに登録するのは不可能だ。チャットボットは一度に一つだけ処理する。

エージェントは違う。「議事録を整理して、そこから出たアクションアイテムをカレンダーに登録して、担当者にメールを送って」と言えば、エージェントはこれを複数のステップに分割して実行する。議事録整理 → アクションアイテム抽出 → カレンダー確認 → メール作成 → 送信。各ステップで必要なツールを自ら選び、途中で問題が起きれば別の方法を試す。

ここで「自ら」が核心だ。チャットボットはユーザーがステップを指示する。エージェントはユーザーが目標を与えれば、エージェントがステップを決める。

## 実際の業務でこの違いがもたらすもの

### ケース1：週次レポート作成

**チャットボット方式**

1. ユーザー：「今週の売上データ要約して」→ AIが要約
2. ユーザー：「先週と比較して」→ AIが比較
3. ユーザー：「レポート形式で整理して」→ AIが整理
4. ユーザー：メールにコピーして送信

3回聞かなければならず、最後は人がやる。

**エージェント方式**

ユーザー：「今週の売上レポートを作ってチームにメールで送って。先週比の変化を含めて、期限は金曜日午前と書いて。」

エージェント:
1. 売上データ確認（ツール：データベース照会）
2. 先週データと比較（ツール：データベース照会）
3. レポート下書き作成
4. メール作成（ツール：メールAPI）
5. ユーザーに下書きの承認を要求
6. 承認 → 送信

ユーザーは目標だけ与え、最後の承認だけする。中間ステップはエージェントが勝手にやる。

### ケース2：顧客問い合わせの分類

チャネルに入ってくる顧客問い合わせを「技術サポート」「決済」「一般」に分類する作業がある。1日に50件。

**チャットボット方式**: 問い合わせを一つずつコピーしてAIに「分類して」→ 分類結果をスプレッドシートに手動入力。50回繰り返す。

**エージェント方式**: 「メールボックスから今日の問い合わせを取ってきて分類して、スプレッドシートに整理して。技術サポートは技術チームチャネルに、決済は財務チームに転送して。」

エージェントはメールボックスを読み、各問い合わせを分類し、スプレッドシートを更新し、チームチャネルにメッセージを送る。50件を一度に。

## エージェントを「いつ」使うのか

エージェントがいつも better とは限らない。以下の条件が合致する時にエージェントに意味がある。

| 条件 | 理由 |
|---|---|
| 複数のステップが必要 | チャットボットはステップごとにユーザーが介入しなければならない |
| 複数のツールを使う必要がある | チャットボットはツールを直接呼び出せない |
| 同じ作業が繰り返される | エージェントの設定コストが繰り返し回数で回収される |
| 途中で失敗する可能性がある | エージェントは失敗時に別のルートを試す |

逆に、一回の質問で終わる作業はチャットボットがいい。「この英語メール翻訳して」をエージェントでやる必要はない。エージェントは設定と維持にコストがかかる。単純な作業をエージェントで包むと、設定コストが効率を食いつぶす。

## 導入前に確認すること

エージェントが勝手に実行してはいけない業務がある。メール送信、決済承認、顧客データの修正。こうした作業はエージェントが「やる」ではなく「下書きを作って人が承認したら実行する」に設計しなければならない。

エージェント導入で最も危険なのは「全部勝手にやってくれるだろう」と任せることだ。現在の技術水準ではエージェントは**確率的に**正しい行動をする。90%は上手くやるが、10%は予想外のことをする。メール送信なんかはその10%が致命的だ。

実務ではエージェントができることとできないことを明確に分け、外部に影響を与える行為（メール送信、ファイル修正、決済）は必ず人が承認するステップを入れる。これが「エージェントを安全に使う」という意味だ。
